# Reporter — Protocol

> Step 3 of 3 in the parity-test-j pipeline. Reads findings.json and the reviewer verdict (passed via dispatch context), renders the final markdown data quality document, writes parity-test-j-report.md to output/.

## Inputs (from dispatch context)

- findings_path — absolute path to findings.json (written by the analyzer step).
- reviewer_verdict — verdict string: approved, approved_with_concerns, or rejected.
- reviewer_notes — full REVIEWER VERDICT block text from the reviewer terminal output.
- report_output_path — absolute path for parity-test-j-report.md (output directory).
- state_path — absolute path to pipeline-state.json.
- run_id — current run ID string.
- root — resolved scope root.

## Protocol

### PHASE 1: VALIDATE INPUT

1. Check that findings_path exists and is readable. If missing: emit BLOCKED. STOP.
2. Parse findings_path as JSON. If parsing fails: emit BLOCKED with parse error detail. STOP.
3. Validate parsed object contains source_path, total_rows, total_columns, analyzed_at, columns array. If any missing: emit BLOCKED. STOP.
4. Confirm reviewer_verdict is approved or approved_with_concerns. If rejected or absent: emit BLOCKED. STOP.

### PHASE 2: COMPUTE SUMMARY METRICS

1. columns_with_issues = count of columns where null_count greater than 0 OR outlier_count greater than 0 OR type_inconsistencies non-empty.
2. total_nulls = sum of null_count across all columns.
3. total_outliers = sum of outlier_count across all columns.

### PHASE 3: RENDER MARKDOWN DOCUMENT

Render the markdown document in this structure:

    # Data Quality Report — parity-test-j
    Source: {source_path}
    Generated: {iso8601_utc}
    Reviewer verdict: {reviewer_verdict}
    ---
    ## Summary Table
    Total rows / Total columns / Columns with issues / Total nulls / Total outliers
    ---
    ## Column Detail
    For each column in original CSV order from columns array:
    Column name as heading, dominant type, null count, outlier count, type inconsistencies (list or none)
    ---
    ## Reviewer Notes
    {reviewer_notes full block}
    ---
    Generated by parity-test-j pipeline (Superpipelines v2.0.0, Tier 1b)

Rules: iso8601_utc is current UTC in YYYY-MM-DDTHH:MM:SSZ. reviewer_notes is the REVIEWER VERDICT block text from dispatch context. Columns in original CSV order.

### PHASE 4: WRITE OUTPUT

1. Ensure root/output/ exists; create if absent.
2. Write rendered markdown to report_output_path as UTF-8 without BOM.

### PHASE 5: UPDATE STATE AND EMIT STATUS

1. Update pipeline-state.json: phases[2].status = completed; phases[2].outputs = [{report_path, total_columns, columns_with_issues}].
2. Emit terminal status:
   - DONE — document written, reviewer_verdict was approved.
   - DONE_WITH_CONCERNS — document written, reviewer_verdict was approved_with_concerns.
   - BLOCKED — validation failed or write failed.

## Invariants

- NEVER load full findings.json into downstream context — operate on the file at findings_path.
- NEVER use hardcoded platform paths. Use paths from dispatch context only.
- NEVER proceed if reviewer_verdict is rejected — halt with BLOCKED.
- ALWAYS validate findings.json schema before rendering.
- ALWAYS write output as UTF-8 without BOM.
- ALWAYS update pipeline-state.json before emitting terminal status.
- Emit exactly one terminal status: DONE / DONE_WITH_CONCERNS / BLOCKED.
